## 1. 「움직이는 중」에 집을 준다

**상태** : ✅ 끝남 (2026-09-18)

**무엇이 문제인가**

`{'running', 'verifying'}` 가 다섯 파일에 **손으로** 적혀 있습니다.

```
bridge_helpers.py:43            midi_control_node.py:1113
playback_session.py:161,183,217 recording_session.py:173
group_session.py:52             ← 여기만 'motion_completed' 가 더 붙어 있다
```

`run_state.py` 가 있지만 **다른 개념**의 주인입니다.

| 개념 | 뜻 | 주인 |
|---|---|---|
| 멈춰 있지 않다 | `initializing` **포함** | `run_state.is_running` |
| 지금 축이 움직인다 | `initializing` **제외** | **없음** ← 이것 |

**무슨 일이 생기나**

새 상태가 하나 생기면 다섯 곳을 고쳐야 하고, 빠뜨린 곳만 조용히 틀립니다.
`group_session` 이 이미 다르게 적고 있습니다 — 의도인지 실수인지 코드만
봐서는 알 수 없습니다.

**어떻게 고치나**

`run_state.py` 에 `is_moving()` 을 두고 다섯 곳이 부릅니다.
`group_session` 의 차이는 그 자리에서 이유를 적거나 없앱니다.

**크기** : 작음 · **위험** : 낮음

**한 일** : `run_state.is_moving()` 을 만들고 다섯 곳이 부르게 했습니다.
`group_session` 의 `motion_completed` 는 **다른 질문**이라 그대로 뒀습니다.

## 2. 화면은 판단하지 않는다

**상태** : 🟡 절반 · 가장 큰 것 하나 끝남 (2026-09-18)

**무엇이 문제인가**

같은 판정을 세 층에서 **따로** 합니다.

```
화면    버튼 비활성     제 나름의 조건
브리지  change_blocker  제 나름의 상태 집합
노드    ValueError      또 제 나름의 조건
```

`ensure_change_allowed` / `change_blocker` 호출이 **11곳**이고, 한 요청이
같은 판정을 두 번 지나는 길도 있습니다.

**무슨 일이 생기나**

2026-09-18 의 버튼 사고가 정확히 이 모양이었습니다. 화면이 제 나름대로
「편집 중」 표시를 세워 두고 저장에 실패하자, 그 표시 때문에 되돌아갈
버튼까지 꺼졌습니다. 서버는 멀쩡했는데 화면만 막혔습니다.

**어떻게 고치나**

서버가 **「왜 안 되는지」를 내려주고**, 화면은 그것을 그대로 보여줍니다.

버튼 비활성 자체는 없애지 않습니다 — 왜 안 되는지 미리 알려주는 것이
맞습니다. 없애는 것은 **화면이 스스로 계산하는 부분**입니다.

**크기** : 중간 · **위험** : 중간

### 2-1. 「모터를 움직일 수 있나」를 화면이 다시 판단했다 ✅ (2026-09-18)

`main.js` 가 같은 판단을 브라우저에서 처음부터 다시 했습니다 — 긴급정지 ·
안전 차단 · 실행 컨텍스트 · 상태 수신 · 모니터링 · 모터 연결.

**임계값까지 따로 들고 있었습니다.**

```
서버   받은 지 1.0초  → '모터 상태 수신이 중단되었습니다'
화면   스냅샷 안 1.5초 → '최신 모터 상태를 확인할 수 없습니다'
```

같은 질문에 두 답이 있으면 언젠가 갈립니다. 버튼은 켜져 있는데 눌러 보면
서버가 거절하거나, 그 반대가 됩니다. 사용자는 프로그램이 고장 났다고 봅니다.

**고침** : 서버가 답하고(`motor_action_blocker`) 스냅샷에 실어 보냅니다 ·
화면은 받아서 보여 주기만 합니다.

**화면에 남긴 것 둘** · 서버가 모르는 것들입니다.

| | 왜 |
|---|---|
| 모터 등록 중 신원 불일치 | 아직 서버에 안 올라온 화면 안의 일 |
| 긴급정지 누른 직후 | 서버 응답을 기다리는 동안 버튼이 살아 있으면 안 됨 |

### 2-2. 조그·절대 위치 판정 정리 ✅ (2026-09-18)

조그와 절대 위치 동작의 판정이 **함수 두 개로 따로** 있었는데, 마지막 한
문장만 달랐습니다. 다이나믹셀 검사 두 줄은 그 안에 한 번씩 또 적혀 있었습니다.

**고침** : `axisActionBlockReason(motor, actionText)` 하나로 합쳤습니다 ·
죽은 함수 둘도 지웠습니다.

**확인한 것** : 스튜디오 버튼들은 이미 **서버가 준 것을 읽기만** 합니다
(`state.composition.conflicts` 등) · 손댈 것이 없었습니다.

### 2-3. 축별 판정이 서버와 화면에 따로 있다 ⬜ 남음

같은 판정이 양쪽에 있고 **문구가 이미 갈렸습니다.**

| 상황 | 서버 `motor_readiness.py` | 화면 `motion_test.js` |
|---|---|---|
| 감지 안 됨 | `Axis 0 is not detected` | `선택 축이 감지되지 않았습니다` |
| 에러 | `Axis 0 has error` | `선택 축에 에러가 있습니다` |
| 서보 OFF | `Axis 0 servo is OFF` | `서보가 켜진 상태가 아닙니다` |

**판정 순서는 같습니다** (detected → servo_on → fault · 다이나믹셀은 servo_on
건너뜀) · 그래서 지금 당장 오동작하지는 않습니다. 다만 한쪽만 고치면
갈립니다.

`motor_readiness.py` 의 설명은 「메시지 문구는 통합 전과 한 글자도 다르지
않다 · 화면과 테스트가 문구를 본다」고 적고 있는데, 실제로 화면은 제 문구를
따로 만듭니다.

**어떻게 고치나** : 서버가 축마다 사유를 상태에 실어 보내고 화면은 읽습니다
(2-1 과 같은 모양).

**왜 아직 안 했나** : 조그는 **리밋에 걸린 축을 빼내는 수단**입니다 · 여기를
잘못 건드리면 복구할 길이 막힙니다 · 전시 운영 중에는 미룹니다.

**진짜 문제는 컨텍스트가 한 덩어리**라는 것입니다 · 무엇이 바뀌든 네 노드가

### 3-1. 한 메서드가 13가지를 만지고 있었다 ✅ (2026-09-18)

18가지 중 **13가지가 한 메서드에 몰려 있었습니다** — `clear_scoped_memory`.

```python
with self.bridge._lock:
    self.bridge._motion_state = None
with self.bridge._motion_run_lock:
    self.bridge._motion_run_status = {}
with self.bridge._midi_monitor_lock:
    self.bridge._midi_monitor_status = {}
self.bridge._midi_monitor_store.clear()
...
```

프로젝트를 다루는 쪽이 브리지의 속살 13가지와 **락 3개**를 알아야 했습니다.

**고침** : 브리지가 제 것을 스스로 버립니다 (`forget_project_memory`) ·
프로젝트 쪽은 「잊어라」 한 마디만 합니다.

**남은 5가지** : `_execution_context` · `_motor_config` ·
`_current_project_generation` · `_ensure_project_mutation_allowed` ·
`_advance_project_generation` · 이것들은 **프로젝트 자체에 딸린 일**이라
성격이 다릅니다 · 다음에 볼 것은 「이 중 프로젝트의 일이 아닌 것이 있나」입니다.

**지키는 법** : `test_services_keep_their_hands_to_themselves.py` 가 서비스마다
가짓수 상한을 둡니다 · 줄이는 건 환영, 늘리면 걸립니다.

## 4. 모션 실행 경로 · 점검 결과

**질문** : 스튜디오·모션 실행·연동 셋이 결국 하나로 모이나? 검사는 한 번인가?

### 모터로 나가는 길 — 하나입니다 ✅

```
모션 스튜디오 ┐
모션 실행    ├→ MotionRunManager · MotionPlayer
연동(그룹)   ┘        └ _publish_positions()          ← 여기 하나
                            ↓  motion_run_command
                        MotionSupervisor
                            └ _command_pub.publish()  ← 최종 관문
                                ↓  motor_command
                              모터
```

셋 다 같은 `MotionPlayer` 를 씁니다 · 그 결과도 곧장 모터로 안 가고
**감시자**가 받아 검사한 뒤 내보냅니다.

**다른 통로 하나** · 수동 조그와 절대 위치 동작은 감시자에게 **직접** 갑니다 ·
의도된 설계입니다 (리밋에 걸린 축을 빼내야 하므로).

### 검사 로직 — 하나입니다 ✅

전부 `plan_builder.build()` 를 지납니다 · 2026-09-18 의 `1-2, 1-3` 사건이
그 증거입니다 · 네 번째 문이 안 막혀 있었는데 **세 경로 모두 똑같이** 거부
됐습니다 · 흩어져 있었다면 어떤 경로만 통과하는 더 나쁜 일이 났을 겁니다.

### 부르는 횟수 — 여럿입니다 (의도된 것이 대부분)

| 언제 | 몇 번 | 왜 |
|---|---|---|
| 단독 재생 | 2 | 재생용 + 초기 이동용 |
| 연동 그룹 | 3 | 검증용 + 재생용 + 초기 이동용 |

셋이 **서로 다른 것을 만듭니다** · `initialization_only=True` 는 첫 프레임만
봅니다 · 그리고 모터 상태가 그 사이 바뀔 수 있어 다시 보는 편이 안전합니다.

### 4-1. 같은 파일을 세 번 읽던 것 ✅ (2026-09-18)

계획을 만들 때마다 **파일을 다시 읽고 파싱**했습니다.

```
실제 파일 183KB · 4,866행
  한 번 45ms  →  연동 시작 한 번에 135ms
```

그 135ms 가 하필 **그룹 동기 시작 직전**에 놓입니다.

**고침** : `mtime` 과 크기를 열쇠로 읽은 것을 들고 있습니다 · 파일이 바뀌면
자동으로 버립니다 · **135ms → 46ms**.

**검사를 줄인 것이 아닙니다** · 계획은 여전히 세 번 만들고 세 번 검사합니다 ·
파일을 다시 읽지 않을 뿐입니다.

**조심한 것** : 돌려주는 목록은 매번 새로 만듭니다 · 부르는 쪽이 거기에
초기 이동 대체값을 덧붙이기 때문입니다 · 같은 목록을 주면 그 값이 다음
계획에 쌓입니다.

## 5. 로그가 시끄러워 진짜 고장이 묻힌다

### 5-1. 정상 거부를 ERROR 로 남기던 것 ✅ (2026-09-18)

이 저장소에서 `ValueError` 는 「사용자에게 보일 거부」의 뜻입니다.

```
포인트 곡선을 만들 Motion ID를 하나만 선택하세요
현재 프로젝트 세대와 다른 요청을 폐기했습니다
잠긴 레이어는 삭제할 수 없습니다
```

이런 것도 **열넉 줄짜리 스택 추적과 함께 ERROR** 로 남았습니다. 이틀치
로그를 세어 보니 ERROR·WARN 의 **절반 이상**이 그것이었습니다.

| 몇 회 | 어디 | 무엇 |
|---|---|---|
| 53 | 스튜디오 에디터 | 포인트 선택 안내 |
| 46 | 모션축 설정 | 세대 불일치 |
| 17 | 모션 실행 | 상태 조회 경합 |

그래서 2026-09-18 에 세 대를 세운 진짜 버그(`sleep length must be
non-negative`)를 찾는 데 반나절이 걸렸습니다.

**고침** : `command_router.log_command_failure()` 하나로 모읍니다 ·
거부는 `warn` 한 줄, 고장은 `error` + 스택 · **아무것도 숨기지 않습니다.**

### 5-2. 연동이 서는 진짜 이유 ⬜ 남음

이틀 동안 그룹이 **6번** 통째로 섰습니다.

```
6회  로컬 Web Bridge 상태 수신 중단: 응답 없음: timed out
     → 그룹 참가 PC 오류 · 전체 정지
```

연동 노드가 50ms 마다 이 PC 의 웹 브리지에게 상태를 묻는데, 300ms 안에
답이 없으면 참가 PC 가 죽은 것으로 보고 세 대를 세웁니다.

같이 나온 것 : `[루프 지연] 104~193ms` **18회** · 예산 500ms 의 40% 까지
씁니다.

**의심** : 웹 브리지가 다른 일(파일 읽기·해시·ROS 왕복)을 하는 동안 그
조회가 밀립니다 · 2026-09-18 에 모션 파일을 세 번 읽던 것(4-1)을 고쳐
135ms 를 줄였으니 나아질 수 있습니다 · **다음 그룹 정지가 나면 그때
`local_runtime_monitor` 의 진단 줄을 보고 판단합니다** (숫자가 남도록
이미 만들어 뒀습니다).

**지금 손대지 않는 이유** : 원인을 모르는 채로 임계값을 올리면 진짜 고장을
못 잡습니다 · 운영 수치는 사용자가 정합니다.

## 이미 고친 것

지운 것이 아니라 **같은 병의 지난 얼굴**입니다. 다시 나오면 여기를 보세요.

### 한 파일에 주인이 셋 (2026-09-18 고침)

`모션1.yaml` 하나에 셋이 들어 있었습니다.

```
mappings        모션축 설정 화면
midi_banks      MIDI 입력 설정 화면
motion_file_id  모션 실행 화면 (재생 등록)
```

MIDI 만 제 길이 있었고 재생 등록은 「설정 전체 저장」 길로 다녔습니다.
그래서 모션 파일만 바꿔도 모션축 설정 개정 검사에 걸렸습니다.

**고침** : 재생 등록에 제 길을 냈습니다 · 개정 번호에서도 뺐습니다.

### 연동이 둘로 갈려 있었다 (2026-09-18 고침)

「그룹 나가기」와 「지금 빠지기」가 따로 있었는데, 멈춰 있을 때는 완전히
같은 일이었습니다. 사용자가 매번 어느 쪽인지 골라야 했습니다.

**고침** : 참가·탈퇴 둘로 합쳤습니다 · 도는 중에는 못 나갑니다.

### 같은 병의 문이 넷이었다 (2026-09-18 고침)

「이 축은 빼고 돌려라」를 네 가지 방법으로 말할 수 있는데, 셋만 막혀
있었습니다. 네 번째(재생 선택 끄기)로 들어오면 모션 전체가 거부됐습니다.

**고침** : 네 번째 문도 막았습니다.
