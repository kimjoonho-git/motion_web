# 모터 설정·검색·실행 구조 재설계안

문서 상태: 설계 기준  
코드 상태: 미구현  
작성 기준: 기존 구현을 유지하기 위한 예외를 추가하지 않고 사용자 목표에서
다시 정의한다.

## 1. 최종 사용자 목표

사용자가 모터 설정 화면에서 직접 수행할 작업은 다음 세 가지뿐이다.

1. `모터 스캔`
2. 필요한 경우 내용 변경 후 `프로젝트 설정 저장`
3. `설정 적용 및 재시작`

적용 성공 후에는 `모션 설정 진행`으로 이동한다. 장치 비교, 실행 세션 생성,
서비스 상태 확인 및 실제 피드백 검증은 프로그램이 자동으로 처리한다.

사용자는 웹에서 이 순서를 완료할 수 있어야 한다. 터미널 작업과 내부 파일
경로 입력을 요구하지 않는다.

## 2. 단일 사용자 흐름

### 새 프로젝트 또는 모터 설정 파일이 없는 경우

`모터 스캔 → 등록 내용 확인·필요한 항목만 편집 → 프로젝트 설정 저장 → 설정 적용 및 재시작 → 모션 설정 진행`

- 검색된 지원 장치를 등록 초안으로 자동 구성한다.
- 사용자는 필요한 경우 축 번호와 축 이름만 변경한다.
- 모델과 시리얼 등 물리 식별정보는 읽기 전용이다.
- `프로젝트 설정 저장` 한 번으로 등록 내용을 확정한다.

### 프로젝트 모터 설정 파일이 있는 경우

`모터 스캔 → 프로젝트 파일과 자동 비교`

- 이미 적용된 프로젝트와 실제 RuntimeFeedback이 일치하는 정상 프로그램
  재시작에서는 사용자 스캔을 다시 요구하지 않는다.
- `모터 스캔`은 최초 장비 연결, 하드웨어 변경, 연결 이상 또는 사용자가
  직접 재검색할 때 실행한다.
- 검색 결과가 같으면 별도 저장 확인을 요구하지 않는다.
- 저장 설정이 현재 실행 설정에도 적용되어 있으면 바로 `모션 설정 진행`을 안내한다.
- 저장 설정이 아직 실행에 적용되지 않았으면 `설정 적용 및 재시작`만 안내한다.
- 검색 결과가 다르면 변경·신규·누락 항목을 한 번에 표시한다.
- 사용자가 `프로젝트에 반영`을 선택하면 프로젝트 파일을 저장한 뒤
  `설정 적용 및 재시작`을 안내한다.
- 사용자가 취소하면 프로젝트 파일과 실행 상태를 변경하지 않는다. 장비를
  조치한 뒤 다시 `모터 스캔`하면 된다.

### 검색 실행 수명주기

사용자는 웹에서 `모터 검색`만 실행하지만 내부에서는 다음 순서를 보장한다.

1. 모션, 조그 및 MIDI 모터 명령이 실행 중이면 검색을 시작하지 않는다.
2. 새 모터 명령을 차단하고 정지 상태를 확인한다.
3. motion_system의 정상 제어 통로로 필요한 안전 정지와 Servo OFF를 수행한다.
4. Motor Manager를 정지하고 EtherCAT Master 사용권 해제를 확인한다.
5. MotorSetupService가 물리 검색을 수행한다.
6. 검색 전에 유효한 RuntimeSession이 있었다면 같은 세션으로 Motor Manager를
   다시 시작하고 새 피드백을 확인한다.
7. 이전 RuntimeSession이 없었다면 실행 대상 없음 상태로 종료한다.
8. 검색 결과와 런타임 복원 결과를 별도로 사용자에게 표시한다.

검색 결과 성공과 이전 런타임 복원 성공을 하나의 성공 상태로 합치지 않는다.

## 3. 분리해야 하는 다섯 데이터

| 데이터 | 의미 | 변경 주체 | 다른 데이터 대체 가능 |
|---|---|---|---|
| PhysicalScanResult | 이번 검색에서 실제 응답한 장치 | 검색 작업 | 불가 |
| ProjectMotorConfig | 현재 프로젝트에서 사용자가 저장한 설정 | 사용자 저장 | 불가 |
| RuntimeSession | 검증된 ProjectMotorConfig의 불변 실행본 | 적용 작업 | 불가 |
| RuntimeFeedback | Motor Manager가 현재 송신하는 실제 상태 | motion_system | 불가 |
| MotionAxisConfig | 모션 ID와 실행 모터축의 연결 | 사용자 저장 | 불가 |

어느 데이터도 값이 없다는 이유로 다른 데이터의 이전 값을 대신 사용하지 않는다.

## 4. 내부 구조

모터 설정 기능은 세 책임으로만 나눈다.

### MotorSetupService

- `MOTOR_SCAN_CONTRACT.md`에 따라 실제 장치를 검색한다.
- 검색 결과와 현재 프로젝트 파일을 자동 비교한다.
- 사용자 승인 후 현재 프로젝트 파일만 저장한다.
- 검색과 저장은 RuntimeSession을 자동 변경하지 않는다.

### MotorRuntimeService

- 저장된 프로젝트 설정을 검증하고 불변 RuntimeSession을 생성한다.
- 프로젝트 ID, 프로젝트 세대, 세션 ID와 설정 SHA-256을 함께 관리한다.
- Motor Manager 시작·정지·재시작과 제한시간을 관리한다.
- 실패 시 검증된 이전 RuntimeSession이 있을 때만 복원한다.

### RuntimeStateMonitor

- Motor Manager의 상태를 RuntimeFeedback으로 변환한다.
- 프로젝트 ID, 프로젝트 세대와 세션 ID를 실행 인자로 받는다.
- 파일 경로를 분석해 프로젝트를 추측하지 않는다.

모터 설정 완료 후의 모션축 설정과 MIDI 제어 허용은 기존 실행 컨텍스트가
검사한다. 모터 설정 화면은 그 내부 조건을 사용자 작업으로 노출하지 않는다.

`motion_system`은 모터 통신과 제어의 단일 통로로 유지한다. 위 구성요소는
motion_system을 우회해 모터 명령을 송신하지 않는다.

## 5. 프로젝트와 실제 장치 비교

### EtherCAT 비교 순서

1. Master 식별자를 확인한다.
2. 유일한 non-zero EEPROM Alias로 기존 장치 후보를 찾는다.
3. Alias가 0이거나 중복이면 Serial Number로 후보를 찾는다.
4. 후보의 Vendor ID, Product Code, Revision 및 표시 모델을 확인한다.
5. Slave Position 변경을 확인한다.
6. 신규 장치와 검색되지 않은 기존 장치를 계산한다.

### Dynamixel 비교 순서

1. 안정적인 직렬 포트 식별자를 확인한다.
2. Bus ID와 Model Number로 기존 장치 후보를 찾는다.
3. ID 변경, 신규 장치 및 검색되지 않은 기존 장치를 계산한다.

### 비교 결과

- `match` · 물리 장치와 프로젝트 설정 일치
- `connection_changed` · 동일 장치의 연결 위치 또는 ID 변경
- `identity_changed` · Alias 또는 고유 식별값 변경
- `model_changed` · 동일 후보의 장치 모델 불일치
- `new_device` · 프로젝트에 없는 실제 장치
- `missing_device` · 프로젝트에는 있으나 검색되지 않은 장치
- `comparison_blocked` · 식별값 없음·중복·검색 불완전

`comparison_blocked`가 하나라도 있으면 자동 반영과 RuntimeSession 적용을
차단하고 정확한 장치와 누락값을 표시한다.

## 6. 저장과 적용

### 프로젝트 저장

- 저장 대상은 사용자가 현재 보고 있는 프로젝트 하나다.
- 검색 결과 원본과 사용자가 정한 축 번호·축 이름을 함께 저장한다.
- 동일 장치는 기존 축 번호와 축 이름을 기본 유지한다.
- 신규 장치는 사용자가 확정한 축 번호로 추가한다.
- 미검색 장치는 사용자 확인 없이 삭제하지 않는다.
- 저장 성공 후 파일을 다시 읽어 저장 내용과 화면 내용을 비교한다.

### 설정 적용 및 재시작

1. 현재 선택 프로젝트를 다시 확인한다.
2. ProjectMotorConfig를 다시 읽고 검증한다.
3. RuntimeSession을 생성한다.
4. Motor Manager를 해당 세션으로 시작한다.
5. RuntimeStateMonitor를 동일한 프로젝트 ID·세대·세션 ID로 시작한다.
6. Motor Manager가 보고한 실행 설정과 요청 세션이 같은지 확인한다.
7. 새 RuntimeFeedback에서 예상 축을 모두 확인한다.
8. 성공을 기록한 뒤 모션축 설정 단계로 이동한다.

파일 생성이나 서비스 프로세스 존재만으로 적용 성공을 판정하지 않는다.

## 7. 사용자 상태

모터 설정 화면은 세부 내부 조건을 나열하지 않고 다음 상태만 표시한다.

- `스캔 필요`
- `스캔 중`
- `내용 확인·저장 필요`
- `적용 및 재시작 필요`
- `적용 중`
- `모터 설정 완료`
- `실패 · 사용자 조치 필요`

`실패` 상태에는 실패 단계, 대상, 원인과 다음 작업 하나만 함께 표시한다.
세부 작업 상태와 로그는 내부에 기록하되 기본 화면에 펼쳐 놓지 않는다.

## 8. UI 기준

기본 화면의 사용자 작업 버튼은 세 개로 제한한다.

1. `모터 스캔`
2. `프로젝트 설정 저장`
3. `설정 적용 및 재시작`

검색 결과 확인은 별도 단계나 버튼으로 만들지 않고 스캔 결과 영역에 바로
표시한다. 프로젝트 파일과 차이가 있을 때만 변경 요약과
`프로젝트에 반영` 확인을 표시한다.

기본 표의 열은 다음으로 제한한다.

- 사용 여부
- 축 번호
- 축 이름
- 모델
- 고유 식별값
- 연결 위치
- 프로젝트 비교 상태
- 실행 상태

Vendor/Product/Revision, 원본 SII 및 작업 로그는 `상세 보기`에서 읽기 전용으로
제공한다. 상단에는 현재 상태와 다음 작업 하나만 표시한다.

## 9. 실패 처리

- 실패 메시지는 `단계 · 대상 · 원인 · 사용자 다음 작업`으로 표시한다.
- 제한시간 초과는 마지막 확인 단계와 실제 서비스 상태를 함께 기록한다.
- 검색 실패를 프로젝트 파일 없음이나 이전 캐시로 성공 처리하지 않는다.
- 적용 실패를 모션축 설정 부족으로 바꾸어 표시하지 않는다.
- 롤백 후 상태는 `이전 실행 복원`, `실행 대상 없음`, `복원 실패`로 구분한다.
- 사용자가 다시 시도할 때 이전 작업의 완료 이벤트가 새 작업에 적용되지 않도록
  operation ID와 session ID를 모두 확인한다.

## 10. 필수 통합 검증

### 코드 검증

- 검색 계약 자동 테스트
- 프로젝트 비교 순서 테스트
- 프로젝트 두 개의 데이터 격리 테스트
- RuntimeSession 경로·SHA·프로젝트 ID 검증
- 상태 모니터가 파일 경로로 프로젝트를 추측하지 않는지 검증

### 실행 검증

1. 설정 없음 → 검색 → 저장 → 재조회
2. 동일 장치 재검색 → 전체 일치
3. 연결 위치 변경 → 변경 감지
4. 신규 장치 → 신규 표시와 사용자 승인 저장
5. 장치 분리 → 미검색 표시, 자동 삭제 없음
6. 설정 적용 → 정확한 RuntimeSession으로 서비스 시작
7. RuntimeFeedback → 예상 축 확인 후 `runtime_ready`
8. 적용 실패 → 이전 실행 복원 또는 실행 대상 없음 확인
9. 프로젝트 A 적용 후 프로젝트 B 선택 → A 상태가 B에 표시되지 않음

### 실물 검증

1. 실제 AC Servo 검색
2. 실제 모터 수와 검색 결과 비교
3. 설정 적용 후 모든 설정 축의 새 피드백 확인
4. 모션축 설정 저장·적용
5. MIDI 입력별 대상 축 확인
6. 제한범위 내 저속·소량 실제 구동

각 단계의 성공을 다음 단계 성공으로 확대하지 않는다.

## 11. 현재 문제의 원인과 재발 방지

### 확인된 원인

- RuntimeSession이 `runtime/sessions/` 구조로 변경됐다.
- RuntimeStateMonitor는 이전 `runtime/파일.yaml` 구조만 프로젝트 실행 파일로
  인정했다.
- 실제 Motor Manager와 5축 피드백은 정상이었지만 상태의 project ID가 비어
  Web Bridge에서 폐기됐다.
- 45초 후 피드백 미수신으로 오판하여 적용 실패와 롤백이 실행됐다.

### 재발 방지 기준

- 최신 코드에서 이전 경로를 추측하는 방식으로 프로젝트 소유권을 결정하지 않는다.
- 프로젝트 ID와 세션 ID는 생성자가 명시하고 모든 소비자가 그대로 검증한다.
- 저장 구조 변경은 RuntimeSession 계약 버전 변경으로 처리한다.
- 단위 테스트 외에 `저장 → 세션 생성 → 서비스 재시작 → 실제 상태 → 웹 ready`
  통합 검증을 완료 조건으로 사용한다.

## 12. 개발 순서

1. 문서 계약 확정
2. 세 가지 사용자 작업과 상태 확정
3. MotorSetupService의 검색·비교·저장 구현
4. MotorRuntimeService의 적용·재시작 구현
5. RuntimeStateMonitor의 경로 추측 제거
6. 실제 적용 통합 테스트
7. 모션축 설정과 MIDI 제어 연결 검증

단계별 검증이 끝나기 전 다음 단계의 완료를 보고하지 않는다.

## 13. 현재 구현 분석과 처리 기준

### 확인된 현재 구조

- Web Bridge 한 클래스가 검색 요청, 프로젝트 저장, RuntimeSession 적용,
  서비스 재시작, 상태 판정 및 API를 함께 담당한다.
- ProjectRepository가 선택 프로젝트, RuntimeSession 대상과 모터 작업 상태를
  여러 상태 파일로 관리한다.
- RuntimeStateMonitor가 Motor Manager 상태 변환과 함께 설정 파일 경로에서
  프로젝트 소유권을 계산한다.
- UI가 물리 검색 결과, 프로젝트 편집 상태와 실행 적용 상태를 한 화면에서
  동시에 조합한다.
- 자동 테스트는 각 함수와 상태 판정을 검증하지만 실제 서비스 재시작과
  ROS 상태 전달 전체를 항상 실행하지 않는다.

### 유지할 기준

- motion_system 단일 모터 통신·제어 통로
- 프로젝트별 데이터 격리
- 내용 해시 기반 불변 RuntimeSession
- 실제 장치 응답만 사용하는 물리 검색
- 작업 ID 기반 동시 실행 제한과 검증된 이전 세션 롤백

### 제거하거나 대체할 구조

- 파일 경로에서 프로젝트 ID를 추측하는 코드
- 이전 프로젝트·검색·런타임 값을 현재 값의 대체값으로 사용하는 fallback
- Web Bridge 한 클래스에 모터 수명주기 책임을 계속 추가하는 방식
- 저장 완료와 실행 준비 완료를 같은 상태로 표시하는 방식
- 사용자가 물리 식별정보나 임의 모델 문자열을 직접 입력하는 UI
- 단위 테스트 통과를 실제 재시작·실물 검증 완료로 확대하는 보고

새 구조는 위 유지 기준만 계약으로 가져가며, 현재 클래스와 함수 배치를
새 설계의 전제로 사용하지 않는다.
